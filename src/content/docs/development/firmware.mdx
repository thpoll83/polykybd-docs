The PolyKybd firmware is a heavily customised QMK build that runs on the keyboard's **Raspberry Pi RP2040**. Two hardware variants share a single firmware codebase: **`split72`** (72-key, RGB matrix, Cirque trackpad, 128×64 status OLED) and **`split42`** (42-key CRKBD footprint, no RGB/trackpad, 128×32 status OLED).

<Aside type="tip">
New to the codebase? Start with [System Model & Data Flow](/development/system-model/) — it
maps the host/master/slave topology, the flash layout, and the runtime processes (boot,
overlays, display power, flashing, multicore) as diagrams before you dig into the source.
</Aside>

## Repository structure

The firmware lives on the `PolyKybd` branch of the QMK fork: [github.com/thpoll83/qmk_firmware](https://github.com/thpoll83/qmk_firmware/tree/PolyKybd), under `keyboards/polykybd/`.

```
keyboards/polykybd/
├── config.h            — pin assignments, PROTOCOL_VERSION, feature flags
├── rules.mk            — build flags, enabled QMK features
├── readme.md           — what each folder holds
├── keys_com/
│   └── poly_keymap.c   — shared keymap logic for BOTH variants:
│                          rendering, HID/overlay handling, language
│                          selection, idle/suspend, split-sync glue,
│                          firmware-update state machine, QMK callbacks
├── lib/
│   ├── hid/
│   │   └── hid_com.c   — raw_hid_receive(): HID command dispatcher
│   ├── display/
│   │   ├── fill_overlay.c   — receives overlay segments, RLE decompress
│   │   └── multicore_exec.c — core1 service loop: overlay decompression and region jobs
│   ├── split_link/
│   │   └── split_sync.c     — CRC32-validated split-half synchronisation
│   ├── system/
│   │   └── state.c     — shared state structs (EEPROM-persisted)
│   └── drivers/
│       └── disp_array.c — per-keycap OLED driver
├── features/           — animations, modes, emoji layer, OS shortcut hints
├── base/
│   └── overlay.c       — overlay image pool (600 × 360 B), addressed via
│                         90 keys × 16 modifier variants
├── lang/
│   └── lang_lut.c      — language lookup table (code-generated via cog)
├── dev/                — tools, scripts, diagnostic and profiling builds
├── split72/            — variant: keymaps/, halconf.h, mcuconf.h, layout data
└── split42/            — variant: keymaps/, halconf.h, mcuconf.h, layout data
```

All behaviour lives in the keyboard-level `poly_keymap.c` (compiled for both variants via `rules.mk`). Each variant's `<variant>/keymaps/default/keymap.c` is **data only** — `keymaps[]`, `encoder_map[]`, and (on RGB variants) `g_led_config`. A feature added to `poly_keymap.c` applies to both keyboards at once, so they always stay the same. The legacy `polykybd.c` / `polykybd.h` still exist, but the bulk of the logic now lives in `poly_keymap.c`.

## Build and flash

Toolchain, QMK CLI, submodules, the `.uf2` and `.bin` outputs and the flash commands are in
[Build & Flash from Source](/howto/build-and-flash/). The firmware runs the RP2040 at 200 MHz with the
core voltage raised to 1.15 V; see [200 MHz System Clock](/beyond-qmk/system-clock/).

## Firmware signing

Released firmware is signed with Ed25519, and the keyboard checks the signature before it installs an update over HID. A build you compiled yourself is unsigned: either sign it with `dev/tools/sign_firmware.py`, or flash it and press **A** on the keyboard when it asks. The full workflow, key rotation and the DOOM pack signature are on [Firmware Signing](/beyond-qmk/signing/).

## Adding a new keymap

Create and edit a keymap as described in [Edit the Keymap](/howto/edit-keymap/#route-2--qmk-firmware-source).
Keep keymap files **data only**. Behaviour belongs in the shared `poly_keymap.c` so both variants stay in sync.

## Display rendering

The per-key OLED displays (72×40 px monochrome) are driven via a custom Adafruit GFX fork. The rendering and overlay logic lives in `keys_com/poly_keymap.c` / `lib/drivers/disp_array.c`.

See [Display Graphics & Fonts](/development/display-graphics/) for the rendering pipeline and the font-generation workflow.

## QMK documentation

All standard QMK features are available. PolyKybd firmware **v0.11.6** is built on
**QMK 0.33.13**. Note that QMK's documentation site is not versioned — there is one
live copy — so when upstream behaviour has changed between releases, check the
[breaking-changes history](https://docs.qmk.fm/breaking_changes_history) rather than
assuming a page matches your build.

The fork tracks upstream's **stable release tags**, not `master` — merging a tag
means the base is a version people can look up, rather than an arbitrary commit.
To check the base of any checkout yourself, rather than trusting this page:

```bash
# The fork's own master is kept as an untouched mirror of upstream QMK,
# so no extra remote is needed — the clone above already has it as origin.
git fetch origin master --tags
base="$(git merge-base HEAD origin/master)"
[ -n "$base" ] || { echo "no merge base — unshallow the clone first" >&2; exit 1; }
git describe --tags --abbrev=0 "$base"
```

<Aside type="caution">
The `[ -n "$base" ]` guard is required. On a shallow clone (the default in some
cloud dev containers) `git merge-base` returns an **empty string** instead of
failing — and an empty argument would leave `git describe` describing `HEAD`, so
without the guard the command reports a wrong tag and no error. If the guard fails, run
`git rev-parse --is-shallow-repository` and then `git fetch origin --unshallow`.
</Aside>

Refer to the [official docs](https://docs.qmk.fm/) for:

- [Keycodes reference](https://docs.qmk.fm/keycodes)
- [Layers](https://docs.qmk.fm/feature_layers)
- [Macros](https://docs.qmk.fm/feature_macros)
- [Tap Dance](https://docs.qmk.fm/feature_tap_dance)
- [Unicode](https://docs.qmk.fm/feature_unicode)

<Aside type="tip">
When working on display-related code, use `--dev 2` with PolyKybdHost to see the raw HID traffic and verify the firmware is sending the expected display commands. See the [HID Protocol Reference](/reference/hid-protocol/) for the command format.
</Aside>
