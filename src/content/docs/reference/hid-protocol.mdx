PolyKybdHost talks to the firmware over a custom **raw HID** report protocol. The same protocol is used by the [HIL test rig](/development/test-rig/) to exercise the firmware in CI.

<Aside type="tip">
For a bird's-eye grouping of these commands by purpose (overlays, identity & language,
configuration, resource flashing) and how they fit the wider system, see the
[System Model & Data Flow](/development/system-model/#the-hid-command-surface) page.
</Aside>

## Report format

Every message is one 64-byte report on the keyboard's raw HID interface (usage page
`0xFF61`, usage `0x62`). The host's HID library puts a report-ID byte `0x00` in front of
each write; the offsets on this page are the 64 bytes the firmware sees, after that byte.

| Offset | Request | Reply |
|---|---|---|
| `[0]` | `0x50` (`P`) | `0x50` (`P`) |
| `[1]` | Command ID | Command ID, echoed |
| `[2]` | First payload byte | Status: `.` (`0x2E`) accepted, `!` (`0x21`) refused |
| `[3..63]` | Payload | Reply body |

- Unused bytes are `0` in both directions.
- PolyKybd's own multi-byte fields are **little-endian**. The QMK keymap commands
  ([below](#qmk-keymap-commands)) keep QMK's big-endian order.
- A report whose `[0]` is not `0x50` goes to the QMK keymap handler instead. (`0x09` in
  `[0]` is also accepted as `P`, for historical reasons.)
- An unknown command is answered with the request echoed back and `[2]` set to `!`.
- The bulk overlay commands get no reply at all; see the note under
  [Resource-flash transport](#resource-flash-transport).

The main dispatcher lives in the firmware's `hid_com.c` (`raw_hid_receive()`); firmware
update (`0x40`–`0x45`) is in `hid_fw_up.c` and the font-pack transport (`0x50`–`0x53`) in
`hid_fontpack.c`. Exact byte layouts for every command are under
[Message formats](#message-formats). The `PROTOCOL_VERSION`, reported inside the
**GET_ID** identity string, tells the host which commands this keyboard understands, so each
feature can be enabled or greyed out individually.

## Command areas

The commands are grouped below by purpose. IDs are shown in hex, with the decimal form where the
source commonly uses it.

### Identity & language

| Command | ID | Notes |
|---|---|---|
| **GET_ID** | `0x06` | Identity string incl. `PROTOCOL_VERSION` and firmware version, plus (v6+) a per-bundle [font-pack](/firmware/font-packs/) version block after the string's NUL. The connect handshake and liveness check. |
| **GET_LANG** | `0x07` | Query the active keyboard language. |
| **CHANGE_LANG** | `0x09` | Select the active language. |
| **GET_LANG_LIST_PACKED** | `0x1b` (27) | **v2+.** Language list as a count byte plus one 2-byte `(ISO 639-1 index, ISO 3166-1 alpha-2 index)` pair per language. The only language-list command on current firmware. |
| **GET_LANG_LIST (ASCII)** | `0x08` | **Retired.** Returned 4 ASCII chars per language; now NACKs (`P\x08!`). |
| **GET_DEFAULT_LAYER** | `0x16` (22) | Read/select the persisted default layer. |

### Overlays — the bulk data path

| Command | ID | Notes |
|---|---|---|
| **SEND_OVERLAY** | `0x0A` | Plain overlay: each 360-byte keycap in 6 × 60-byte segments. (v11 packs modifier + segment into one header byte so a 60-byte segment fits the report exactly.) |
| **START / SEND_COMPRESSED_OVERLAY** | `0x10` / `0x11` | RLE-compressed keycap in 1–2 packets; decompressed in firmware (optionally on RP2040 core1). The common case. |
| **START / SEND_ROI_OVERLAY** | `0x12` / `0x13` | Partial refresh of a region of a keycap's display. |
| **SEND_PRC_OVERLAY** | `0x29` (41) | **v19+.** [PRC](#prc-predictive-range-coding)-coded keycap images, several records per report. A typical icon codes to about a third of the bytes of the best older encoding. |
| **FILL_POOL_FROM_ICON** | `0x2A` (42) | **v20+.** Fills pool slots from the [icon library](#icon-library-fills) in the keyboard's flash: `(pool slot, icon id)` pairs instead of bitmaps. The one bulk overlay command that replies. |
| **SEND_OVERLAY_MAPPING** | `0x15` (21) | Maps overlay pool slots to displays / usage bits, at a fixed 10 bits per index. **Silent since v3** (no per-chunk ACK). The only mapping command a pre-v12 keyboard understands. |
| **SEND_OVERLAY_MAPPING_W** | `0x21` (33) | **v12+.** The same mapping stream, but a width byte says how many bits each index uses (8–11), so the host packs each group of pairs as tightly as it fits. Also silent. Since **v21** two bits of the width byte can also run the prepare and enable steps of an app switch; see [mapping flags](#mapping-flags). |
| **OVERLAY_FLAGS on / off** | `0x0B` / `0x0C` | Enable/disable overlay rendering; enable force-syncs overlay state to the slave. From v21 the prepare and enable steps of an app switch can ride on the mapping reports as [flags](#mapping-flags) instead. The host still sends the prepare as its own report before any image upload, and sends both as their own reports when a switch has no mapping report. `off` is unchanged. |
| **SAVE_MRU** | `0x1A` (26) | Persist the keyboard's most-recently-used emoji / language picks. Unrelated to the host's overlay cache. |

### Configuration & display

| Command | ID | Notes |
|---|---|---|
| **SET_BRIGHTNESS** | `0x0D` (13) | Keycap OLED contrast; a flags byte selects volatile / host-auto (**v5+**). |
| **KEYPRESS** | `0x0E` (14) | Host-injected key event. Refused (`!`) unless debug mode is on. |
| **IDLE_STATE** | `0x0F` (15) | Start / stop the [idle](/using/idle/) animation. |
| **SET_UNICODE_MODE** | `0x14` (20) | Select the OS unicode-input mode. Since **v17** a flag byte can apply it for this session only, leaving the stored mode alone. |
| **DISPLAY_OFF** | `0x18` (24) | Blank the keycaps. |
| **IDLE_STYLE** | `0x1C` (28) | **v4+.** Get/set the idle style (pulse / jitter). |
| **SET_OS** | `0x1D` (29) | Active host OS → modifier legends. |
| **GLYPH_SCRIPT** | `0x1E` (30) | **v9+.** Get/set the [glyph-script](/using/glyph-scripts/) override (open-ended index since v10). |
| **GLYPH_SIZE** | `0x22` (34) | **v13+.** Get/set the [legend size](/using/legend-size/) — how large a key's main legend is drawn. A closed range (0 small / 1 medium / 2 large); anything else NACKs. |
| **GET_LAYER_NAMES** | `0x23` (35) | **v14+.** Read-only. The keyboard reports how many layers it lets you remap and what each is called — the labels the [layout editor](/using/keymap-editor/) puts on its layer tabs. The reply leads with its own total length, then the count, then one NUL-terminated name per layer. |
| **MACRO_INFO** | `0x24` (36) | **v15+.** How many [macros](/using/macros/) the keyboard holds, how long a label may be, and how much of the shared body buffer is used. Read-only. |
| **MACRO_BODY** | `0x25` (37) | **v15+.** Read or write a window of the shared macro body buffer — offset, count, bytes. The bodies are NUL-separated, so the host reads the whole buffer, edits one and writes it back. |
| **MACRO_LABEL** | `0x26` (38) | **v15+.** Get/set one macro's label — the short text the keycap spells out along its bottom edge. |
| **CRASH_RECORD** | `0x27` (39) | **v16+.** Read the keyboard's last [crash record](/software/reporting-problems/#when-the-keyboard-firmware-crashes) — `0` this half, `1` the link-side half (pulled over the split link), `2` clears it. The reply is a flags byte (present / fresh) and the 48-byte record: crash kind, core, the faulting `pc`/`lr`/`sp`, what the firmware was doing, uptime and firmware version. |
| **IDLE_TIMEOUT** | `0x28` (40) | **v18+.** Get/set how long the keyboard waits before it starts [fading into the idle style](/using/idle/#how-long-before-it-idles) — a preset index (0 = 15 sec … 5 = 5 min), or `0xFF` to query. A closed range like `GLYPH_SIZE`: anything else NACKs. The reply carries both the preset **and** its duration in seconds, so a host older than the keyboard can still label a preset it has never heard of. |
| **REBOOT** | `0x2B` (43) | **v22+.** Restart both halves and save nothing. The keyboard answers before it resets. It exists for the host's [boot-loop test](/software/reporting-problems/#catching-a-crash-that-only-happens-now-and-then), which reboots hundreds of times. |
| **BOOTLOADER / HANDEDNESS** | `0x17` / `0x19` | Enter bootloader; set which half is which. |

### Layer names — the reply format

`GET_LAYER_NAMES` answers with a payload that describes its own length, so a reader
knows when it has the whole thing without waiting for a timeout:

| Offset | Bytes | Meaning |
| --- | --- | --- |
| `0` | 1 | **total** — the whole payload length, this byte included |
| `1` | 1 | **count** — how many layers are named |
| `2…` | rest | `count` NUL-terminated ASCII names, at most 8 characters each |

With today's eight remappable layers that is 54 bytes, which fits a single 64-byte
report (three of which are the `P`, command and status header). A longer set simply
spans more reports; the reader concatenates each report's payload and stops once it
holds `total` bytes.

Two details follow from carrying the total rather than padding each name to a fixed
width. The zero fill at the end of the final report is never examined, because the
total already says where the names stop — so it can't be mistaken for a separator.
And a layer with **no** name is expressible: it is simply an empty entry, which stays
distinguishable from that fill.

### Resource-flash transport

Two command sets share one BEGIN / CHUNK / COMMIT flow and one staging code path in the
firmware:

| Command | ID | Notes |
|---|---|---|
| **FW_UP_BEGIN** | `0x40` | Firmware image: size and CRC; both halves start erasing staging. |
| **FW_UP_CHUNK** | `0x41` | 56 bytes at an offset; relayed to the slave. |
| **FW_UP_COMMIT** | `0x42` | Check CRC and signature on both halves. |
| **FW_UP_GET_VERSION** | `0x43` | Running version, size and CRC. |
| **FW_UP_APPLY** | `0x44` | Install the staged image on both halves and reboot. |
| **FW_UP_SIGNATURE** | `0x45` | Ed25519 signature, two 32-byte parts, before COMMIT. |
| **FONTPACK_BEGIN** | `0x50` | Font-pack bundle, DOOM WAD or DOOM engine pack: size, CRC and target slot. |
| **FONTPACK_CHUNK** | `0x51` | 56 bytes at an offset; relayed to the slave. |
| **FONTPACK_COMMIT** | `0x52` | Check CRC on both halves and reload the fonts. No reboot. |
| **FONTPACK_STATUS** | `0x53` | Whether a pack is present, its ABI, content version and font count. |

The whole update flow is described in [Firmware Update over HID](/beyond-qmk/firmware-update/).

A firmware update may additionally carry an **Ed25519 image signature** (command `0x45`, sent
before COMMIT) that the keyboard verifies against a key built into its firmware. It is **additive**
— older hosts simply never send it, so there is no `PROTOCOL_VERSION` bump — and it is now
**enforced**. See [Firmware Signing](/beyond-qmk/signing/) and
[Firmware Update over HID](/beyond-qmk/firmware-update/).

Enforcement gives the firmware COMMIT four status bytes rather than two:

| Byte | Meaning |
|---|---|
| `.` | Accepted — the staged image verified. |
| `?` | Awaiting a physical **ACCEPT/REJECT** on the keycaps (unsigned image). Re-poll COMMIT until it changes; the staged image and its CRC are untouched between polls. |
| `S` | Refused — not validly signed (rejected at the prompt, timed out, or the signature failed to verify). |
| `!` | Staged-CRC mismatch. |

`?` and `S` are why the refusal reason is no longer guessed from a bare NACK. A COMMIT carrying
`'x'` in `[2]` **cancels** a pending prompt — safe to expose over HID because it can only ever
deny, whereas accepting stays a keypress on the board.

<Aside type="caution">
A host that predates `?` has no case for it, falls into its generic failure branch and leaves the
progress dialog stalled while the keyboard stays modal for its full 60 s window. Update
PolyKybdHost before flashing an unsigned image.
</Aside>

<Aside type="note">
The bulk overlay commands (`0x0A`, `0x10`/`0x11`, `0x12`/`0x13`, `0x29`, and mapping on v3) are **not** ACK'd per chunk — the host follows a burst with a `GET_ID` liveness check rather than waiting for replies. `0x2A` is the exception: the host needs its answer to know which icons it still has to upload.
</Aside>

## Message formats

Offsets are into the 64-byte report (see [Report format](#report-format)). `[0]` is always
`0x50` and `[1]` the command ID, so the tables start at `[2]`. A reply's `[2]` is the
status byte (`.` / `!`) unless the table says otherwise. `u16` and `u32` are
little-endian. "—" means no payload.

### Identity and language

| ID | Request `[2..]` | Reply `[3..]` |
|---|---|---|
| `0x06` GET_ID | — | Status `[2]` is `*` instead of `.` on the first GET_ID after a boot. ASCII `<board> <fw version> P<protocol> HW<hw version> `, NUL; then `V`, `n`, `n × u16` font-pack bundle versions; then `G`, `u16` state generation. A block that does not fit is left out whole. |
| `0x07` GET_LANG | — | `[3..6]` language code, 4 ASCII (`deDE`) |
| `0x09` CHANGE_LANG | `[2..5]` language code, 4 ASCII | — (`!` if unknown) |
| `0x16` GET_DEFAULT_LAYER | — | `[3]` default layer |
| `0x1B` GET_LANG_LIST_PACKED | — | Several replies, each `[3..63]` up to 61 bytes. Joined: `count`, then `count ×` (ISO 639-1 index, ISO 3166-1 index), indices into the frozen table `iso_lang_country.py`. |

### Settings

| ID | Request `[2..]` | Reply `[3..]` |
|---|---|---|
| `0x0B` OVERLAY_FLAGS on | `[2]` flags to set: bit 0 show overlays, 1 map all, 2 mirror to both halves, 5 reset buffers, 6 reset usage, 7 reset mapping | — |
| `0x0C` OVERLAY_FLAGS off | `[2]` flags to clear, same bits | — |
| `0x0D` SET_BRIGHTNESS | `[2]` level `0..50`; `[3]` flags: bit 0 volatile, bit 1 auto on, bit 2 auto off | — (`!` if level > 50) |
| `0x0E` KEYPRESS | `[2..3]` keycode, **big-endian**; `[4]` `0` press, else release | — (`!` unless debug mode is on, see below) |
| `0x0F` IDLE_STATE | `[2]` `0` wake, else start idle | — |
| `0x14` SET_UNICODE_MODE | `[2]` `0` Linux, `1` macOS, `2` Windows, `3` WinCompose, `4` BSD; `[3]` non-zero = this session only (v17) | — |
| `0x17` BOOTLOADER | — | — then the keyboard enters the bootloader |
| `0x18` DISPLAY_OFF | — | — |
| `0x19` SET_HANDEDNESS | `[2]` `0` = the USB half is left, else right | — then both halves reboot |
| `0x1A` SAVE_MRU | — | — (writes unsaved settings to EEPROM) |
| `0x1C` IDLE_STYLE | `[2]` `0xFF` query, or `0` pulse, `1` jitter, `2` DOOM demo, `3` Eden | `[3]` style |
| `0x1D` SET_OS | `[2]` `0xFF` query, `0xFE` auto, or OS: `0` unknown, `1` Windows, `2` macOS, `3` Linux, `4` Android, `6` GNOME, `7` KDE; `[3]` bit 0 = pin (manual) | `[3]` active OS, `[4]` `1` if auto |
| `0x1E` GLYPH_SCRIPT | `[2]` `0xFF` query, or script `0..0xFE` (any value accepted) | `[3]` script |
| `0x1F` REPLAY_ANIM | — | — |
| `0x20` PROFILER | `[2]` `0` reset, `1` read, `2` log; `[3]` page (read) | `[3]` page, `[4..]` snapshot. Profiler builds only; others answer `!`. See [Main-Loop Profiler](/beyond-qmk/loop-profiler/). |
| `0x22` GLYPH_SIZE | `[2]` `0xFF` query, or `0` small, `1` medium, `2` large | `[3]` size (`!` if out of range) |
| `0x23` GET_LAYER_NAMES | — | See [Layer names](#layer-names--the-reply-format) |
| `0x28` IDLE_TIMEOUT | `[2]` `0xFF` query, or preset `0..5` (15 s, 30 s, 45 s, 1 min, 2 min, 5 min) | `[3]` preset, `[4..5]` `u16` seconds (`!` if out of range) |

`KEYPRESS` makes the keyboard type into whatever app has focus, so any program that can
talk raw HID could use it to inject keystrokes. The firmware therefore refuses it unless
debug mode is on. Debug mode is off at every boot and is switched on with the `DB_TOGG`
key on the settings layer, which needs a hand on the keyboard.

### Macros and crash record

| ID | Request `[2..]` | Reply `[3..]` |
|---|---|---|
| `0x24` MACRO_INFO | — | `[3]` macro count, `[4]` max label length, `[5..6]` `u16` buffer capacity, `[7..8]` `u16` bytes used, `[9]` keycap styles drawn |
| `0x25` MACRO_BODY | `[2]` `0` read, `1` write; `[3..4]` `u16` offset; `[5]` count (≤ 58); `[6..]` bytes (write) | Read: `[3]` count, `[6..]` bytes. Write: status only. |
| `0x26` MACRO_LABEL | `[2]` macro id; `[3]` `0xFF` query, else caption length; `[4]` style; `[5..8]` `u32` icon code point; `[9..]` caption, ASCII | Same layout from `[3]`: length, style, icon, caption |
| `0x27` CRASH_RECORD | `[2]` `0` this half, `1` other half, `2` clear | `[3]` flags: bit 0 present, bit 1 fresh; `[4..51]` record (below) |

The 48-byte crash record, from `[4]`:

| Offset | Type | Field |
|---|---|---|
| `+0` | `u32` | magic |
| `+4` | `u8` × 4 | kind (`1` HardFault, `2` unhandled interrupt, `3` watchdog, `4` halt), core, consecutive count, reset reason |
| `+8` | `u32` × 6 | `pc`, `lr`, `sp`, `xpsr`, `icsr`, uptime in ms |
| `+32` | `u16` × 2 | phase, phase argument |
| `+36` | 8 chars | firmware version, NUL-padded |
| `+44` | `u32` | CRC-32 of the 44 bytes before it |

### Overlay uploads

No reply, except `0x2A`. A keycap image is 72 × 40 pixels, **360 bytes**: row-major,
9 bytes per row, most significant bit = leftmost pixel, `1` = lit. `keycode` is the HID
usage of the key (`KC_A` … `KC_RGUI`); `mod` is the modifier variant `0..15` from
[Overlay addressing](#overlay-addressing).

| ID | Report layout |
|---|---|
| `0x0A` SEND_OVERLAY | `[2]` keycode; `[3]` bits 0–3 mod, bits 4–7 segment `0..5`; `[4..63]` bytes `60 × segment` to `60 × segment + 59` of the image |
| `0x10` START_COMPRESSED | `[2]` keycode; `[3]` mod; `[4..63]` first 60 bytes of the [RLE](#rle-overlay-encoding) stream |
| `0x11` SEND_COMPRESSED | `[2..63]` next 62 bytes of the RLE stream |
| `0x12` START_ROI | `[2]` keycode; `[3..6]` ROI header (below); `[7..63]` first 57 bytes of ROI data |
| `0x13` SEND_ROI | `[2..63]` next 62 bytes of ROI data |
| `0x15` SEND_OVERLAY_MAPPING | `[2..63]` 10-bit values, packed least significant bit first |
| `0x21` SEND_OVERLAY_MAPPING_W | `[2]` bits 0–4 width `8..16`, bit 5 show after, bit 6 prepare before ([mapping flags](#mapping-flags)); `[3..63]` values of that width, packed least significant bit first |
| `0x29` SEND_PRC_OVERLAY | `[2..63]` [PRC records](#prc-predictive-range-coding) |
| `0x2A` FILL_POOL_FROM_ICON | `[2]` width `8..16`, with **no** flag bits (a set bit 5 or 6 makes the width out of range and the report is refused); `[3..63]` (pool slot, icon id) pairs, packed least significant bit first. Reply: `.` if every pair applied, else `!` and `[3]` = index of the first pair the host must upload as a bitmap. |

The mapping values come in pairs: an overlay index, then the pool slot it shows. A report
that has fewer pairs than it holds is padded by repeating the last pair.

ROI header, `[3..6]` of `0x12`. `top`/`left` are the first row and column, `bottom`/`right`
the row and column one past the end:

| Byte | Bits 7–4 | Bits 3–2 | Bits 1–0 |
|---|---|---|---|
| `[3]` | `top` bits 5–2 | `mod` bits 3–2 | `mod` bits 1–0 |
| `[4]` | `bottom` bits 5–2 | `bottom` bits 1–0 | `top` bits 1–0 |
| `[5]` | `left` (bits 6–0) | | |
| `[6]` | bit 7: data is RLE-coded; bits 6–0: `right` | | |

ROI data is the rectangle's pixels, row-major, packed with no padding between rows,
most significant bit first.

### QMK keymap commands

These follow QMK's dynamic-keymap protocol: there is no `P`, `[0]` is the command, and
multi-byte values are **big-endian**. The reply is the request echoed back, with read
data filled in. Commands not listed get no reply.

| `[0]` | Command | Request | Reply |
|---|---|---|---|
| `0x05` | set keycode | `[1]` layer, `[2]` row, `[3]` column, `[4..5]` keycode | echo |
| `0x06` | reset keymap | — | echo |
| `0x11` | get layer count | — | `[1]` count of remappable layers |
| `0x12` | get buffer | `[1..2]` byte offset, `[3]` size (≤ 60) | `[4..]` keymap bytes |
| `0x13` | set buffer | `[1..2]` byte offset, `[3]` size (≤ 60), `[4..]` bytes | echo |

The keymap buffer is `layer × rows × columns` keycodes, 2 bytes each, big-endian, as in
upstream QMK.

## RLE overlay encoding

The compressed uploads (`0x10`/`0x11`, and `0x12`/`0x13` with the RLE bit) use a bit-run
encoding: each byte describes one run of identical pixels.

- **Input**: the image read as a bit stream, most significant bit of each byte first. For
  a whole keycap that is all 2880 pixels; for an ROI, the rectangle's pixels.
- **One byte per run.** Bit 7 is the pixel value of the run, bits 0–6 its length,
  `0..127`. A run longer than 127 is split: 300 lit pixels are `FF FF AE`.
- **The stream starts with a run of unlit pixels.** An image whose first pixel is lit
  begins with `00`, an empty run.
- **Empty runs decode to nothing.** That is why the zero fill after the last data byte of
  the final report needs no length field: every `00` is a run of no pixels.

Example, 16 pixels `0000 0111 1111 1000`: 5 unlit, 8 lit, 3 unlit, coded as `05 88 03`.

The firmware decoder is `rle_decompress()` in the
[`polymod_rle`](/beyond-qmk/community-modules/) module. It takes the bit position to
continue from, so each report is decoded on arrival without buffering the whole stream,
and it stops at the end of the 360-byte image whatever the stream says. For a whole
keycap it runs on [core1](/beyond-qmk/core1/) where available. For an ROI, the firmware
decodes one run byte at a time (at most 127 pixels) and places the pixels into the
rectangle row by row.

The host encoder is `polyhost/util/rle_util.py`. RLE pays off on large uniform areas and
loses on detailed or dithered images, where runs are 1–2 pixels and each costs a byte
that plain data would spread over 8 pixels. The host therefore sizes each image in every
encoding (plain, RLE, ROI, ROI with RLE, and [PRC](#prc-predictive-range-coding) from
v19) and sends the one that needs the fewest reports.

## PRC: Predictive Range Coding

Since **v19** the host has a fifth encoding for keycap images: **PRC**, short for
*Predictive Range Coding*. Host and firmware must both be on v19 or later; with an older
keyboard the host keeps using the four older encodings.

PRC is a context-model binary arithmetic coder, the scheme of [JBIG](https://en.wikipedia.org/wiki/JBIG), the fax-image standard [ITU-T T.82](https://www.itu.int/rec/T-REC-T.82):

- **Context model.** Before a pixel is decoded, 10 already-decoded pixels in a fixed causal
  template (3 pixels two rows up, 5 one row up, 2 to the left in the same row) form a
  10-bit context, 0–1023. A fixed
  1 KB table maps each context to P(pixel is clear). Keycap icons are mostly clear area and
  clean stroke edges, so for most pixels the table's prediction is near 0% or 100%.
- **Range coding.** A binary range coder turns those probabilities into bits. A pixel's code
  length is its information content, −log₂ p, where p is the probability the table gave its
  actual value: a correctly predicted pixel costs a fraction of a bit, a mispredicted one
  several bits. The table was trained once on the shipped overlay templates and is compiled
  into the firmware.

![The causal context template: the pixel being decoded, marked with a question mark, and the ten already-decoded pixels that form its context, numbered 6, 7, 8 two rows above; 9, 1, 2, 3, 10 one row above; 4 and 5 to the left](../../../assets/reference/prc-stencil.svg)

**Where the template comes from.** Three decisions shape it, and only one of them was
trained:

- **Which 10 pixels: taken from JBIG unchanged, not measured.** PRC uses the pixel pattern
  of JBIG's three-line template, defined in [ITU-T T.82](https://www.itu.int/rec/T-REC-T.82).
  JBIG lets the encoder move one of the five pixels in the row above, the adaptive pixel;
  PRC keeps it at its default place, two columns right. No other set of positions was
  compared on the keycap icons.
- **The numbering 1–10: our own convention, not JBIG's.** It sets which neighbour is the context's most
  significant bit: the five nearest first, then the five farther ones. Any order gives the
  same compression, because reordering the bits only relabels the 1,024 contexts. Each
  context still collects the same pixels during training, so every probability and every
  code length stays the same. The order is frozen only because host and firmware must agree
  on it.
- **The table: trained.** For each of the 1,024 contexts, the training counted how often the
  pixel is clear across the shipped overlay templates. This is the only part that comes from
  the data.

Only the bounding box (ROI) of the set pixels is coded. A typical icon's coded payload is about
28 bytes, against about 87 for the best of the older encodings. Each record adds a 6-byte header,
and a report carries 62 bytes after its `P` and command byte. So most icons need one report, and
two records share one when together they fit in 62 bytes. Across the 118 shipped templates, the image reports of an uncached app
switch fall to 40% (4348 → 1753); a JetBrains IDE goes from 205 to 81.

The host decides per image: an image goes out as PRC only if its record fits one report, which
is never more reports than an older encoding would take. Larger images keep the old path.

### Worked example: a 10 × 10 square

Take a solid 10 × 10 square: a 100-pixel ROI with every pixel set. Uncoded, it takes 100 bits
(13 bytes). The coder visits the pixels in raster order. Context pixels outside the ROI count
as clear.

| Pixel (row, column) | Context | P(set) from the table | Code length |
|---|---|---|---|
| (0, 0), first pixel | all 10 outside the ROI, so all clear | 1.6% | 6.0 bits |
| (0, 1) | left neighbour set | 86% | 0.21 bits |
| (1, 0) | row above set, left neighbours clear | 80% | 0.31 bits |
| (1, 5) | row above and left neighbours set | 99.6% | 0.006 bits |
| (5, 5) | all 10 set | 95% | 0.075 bits |
| (9, 9), last pixel | set, but the upper-right context pixels lie outside the ROI | 80% | 0.32 bits |

The figure shows the code length of all 100 pixels. The colour scale runs from dark blue
(predicted, near zero bits) to red (mispredicted):

![A 10 by 10 grid, one cell per pixel of the square, each labelled with its code length in bits: 6.0 for the first pixel, about .2 along the top row, .31 to .39 down the left column, .006 along the second row and column, .08 in the interior, and .17 to .32 along the right edge](../../../assets/reference/prc-square-costs.svg)

Only the first pixel is mispredicted. Every later pixel matches the prediction, so the 100
pixels together carry 19.2 bits of information. The coder's initial and flush bytes bring the
payload to **6 bytes**, and the record to 12.

The table was trained on real icons, which are mostly 1–2 px strokes. So a pixel whose whole
context is set (95%) is predicted less confidently than one continuing a stroke edge (99.6%):
large filled areas are rare in the training set.

### Worked example: a real icon

VS Code's `Ctrl+P` (*Quick Open*) shows the Fluent *Document Search* icon. Its set pixels fit a
27 × 31 px ROI (orange) in the right half of the 72 × 40 px keycap, rows 7–37 and columns 37–63:

![VS Code's Quick Open icon, a page with a folded corner and a magnifying glass, drawn in the right half of a 72 by 40 pixel keycap grid; an orange rectangle marks the 27 by 31 pixel ROI that PRC codes](../../../assets/reference/prc-quick-open.png)

| Encoding | Bytes | Reports |
|---|---|---|
| Plain (`0x0A`) | 360 | 5 (all-clear segments are skipped) |
| RLE, whole keycap (`0x10`/`0x11`) | 154 | 3 |
| ROI, uncompressed (`0x12`/`0x13`) | 105 | 2 |
| ROI, RLE (`0x12`/`0x13`) | 139 | 3 |
| **PRC** (`0x29`) | **26 + 6-byte header** | **1, with 30 bytes left** |

The best older encoding needs 2 reports. The PRC record is 32 bytes, which leaves 30 of the
report's 62 bytes. The next record joins it if its whole record, header included, fits in those
30 bytes; otherwise it starts a new report.

Where do the 26 bytes go? The next figure colours each of the ROI's 837 pixels by its code
length, on the same scale as the square; set pixels have a white outline:

![The Quick Open icon as a code-length map. Most of the ROI is dark blue, meaning under 0.1 bit per pixel. Orange and red pixels sit where a stroke starts, ends or turns. Three pixels are circled: A, where the page's bottom edge starts after the magnifier's handle, 6 bits; B, just past the end of the handle, 4.3 bits; C, inside the page's right edge, 0.01 bits](../../../assets/reference/prc-quick-open-costs.svg)

- **A** is set where the table gave P(set) = 1.6%: the page's bottom edge resumes after the gap
  for the magnifier's handle, and no context pixel indicates it. 6 bits, the same as the
  square's first pixel.
- **B** is clear where the table gave P(set) = 94.9%: the context matches a continuing stroke,
  but the handle ends there. 4.3 bits.
- **C** lies inside the page's right edge. The context is unambiguous, P(set) = 99.2%, and the
  pixel costs 0.01 bits.

Most of the ROI behaves like C. 610 of the 837 pixels (73%) cost under 0.1 bit each, 18 bits
in total. 43 pixels (5%), the stroke starts, ends and corners, carry 61% of the 185.6 bits.
That is why PRC gains the most on line icons: long strokes, few stroke ends.

### One row, pixel by pixel

The coder handles the ROI one row at a time, left to right. Row 2 of the ROI (keycap row 9)
is the page's top edge below the folded corner. Rows 0 and 1 above it are already decoded:

![Row 2 of the Quick Open ROI as 27 cells, each labelled with its code length, below the two decoded rows 0 and 1 in grey (set) and dark (clear). Two dashed columns on each side lie outside the ROI. Around column 4 the ten context pixels are outlined in orange and numbered 1 to 10](../../../assets/reference/prc-quick-open-row.svg)

Column 4 shows how a context is formed. Its 10 neighbours, in template order, read
1 1 1 0 1 0 1 1 0 1. Neighbour 1 is the most significant bit, so the context is
`1110101101` in binary, 941. Table v1 holds 2 at index 941: P(clear) = 2/256, so
P(set) = 99.2%. The pixel is set and costs −log₂ 0.992 = 0.011 bits.

Read from left to right:

- **Columns 0–1** are clear. At most one context pixel is set (neighbour 10 of column 1),
  so P(set) is 1.6–5.1% and each pixel costs under 0.1 bit.
- **Column 2** is clear, but neighbours 3 and 10 are set: the page's top edge starts above
  and to the right. The table gives P(set) = 62.1%, and the pixel costs 1.4 bits.
- **Columns 3–5** are the page's left edge, predicted at 87.9–99.2%: 0.01–0.19 bits each.
- **Column 6** has all 10 neighbours set and P(set) = 94.9%, but it is clear: the page's
  interior starts here. 4.3 bits, more than a third of the row.
- **Columns 7–14** are the page's interior below the set top edge. The table gives
  P(set) = 8.6–10.5% here, against 1.6% in open space, so these clear pixels cost
  0.13–0.16 bits each.
- **Column 15** has the same context as columns 8–14, but it is set: the fold's diagonal
  starts. 3.5 bits.
- **Columns 16–18** continue the diagonal, predicted at 71.5–99.6%.
- **Columns 19–26** lie right of the fold and are clear: 0.01–0.47 bits each.

The 27 pixels carry 11.9 bits of information; uncoded they take 27. The three mispredicted
pixels, columns 2, 6 and 15, carry 9.2 of those 11.9 bits. The range coder emits no bits per
pixel: it narrows one interval by each pixel's probability, so the payload follows the sum
over the whole ROI. For this icon that is 185.6 bits, which the coder writes as 26 bytes,
including its start and flush overhead.

**Report layout.** After `P` and `0x29`, the report carries records back to back. A keycode byte
of 0 (the zero padding) ends the list.

| Field | Bits | Content |
|---|---|---|
| keycode | 8 | Addresses the image like the other upload commands |
| modifier | 4 | Modifier variant 0–15 |
| top, left | 6, 7 | Top-left corner of the ROI |
| height − 1, width − 1 | 6, 7 | ROI size |
| length | 6 | Payload bytes that follow |
| reserved | 4 | Must be 0 |
| payload | length × 8 | The range-coded ROI |

<Aside type="caution">
The table is part of the format. Host and keyboard must use the identical 1 KB table, or the
keycaps show garbage and nothing reports an error. A retrained table would be a new protocol
version, never a change to table v1.
</Aside>

## Icon library fills

Since **v20** the icons that the app templates share live in the keyboard's flash, on both
halves, as one more font-pack bundle: `icons.plyi`, bundle 8, a 256 KB slot. When the host
switches app, it no longer uploads such an icon. It sends a pair instead: which pool slot to
fill, and which icon to draw there. Each half draws the icon from its own flash.

The host decides by exact pixels. It fills a slot only when the image it would upload is,
byte for byte, a glyph in the bundle it shipped, and only when the keyboard reports that same
bundle version. So the keycap shows exactly what an upload would have shown. Anything else
(an app's own drawings, text labels, the ESC program mark) is uploaded as before, with PRC.

**What it saves.** Counted through the host's own send path, for a cold switch into each app
(nothing in the keyboard's image pool yet), on top of PRC:

| App | Reports with PRC | With the icon library |
|---|---|---|
| JetBrains IDEs | 84 | 32 |
| Calculator | 64 | 9 |
| paint.net | 59 | 11 |
| Photoshop | 46 | 15 |
| All 60 template sets | 1,868 | 744 |

**The report** uses the same packing as `SEND_OVERLAY_MAPPING_W`: byte 2 is the value width
(8–16 bits), then 61 bytes of `(pool slot, icon id)` pairs, padded by repeating the last pair.
At 10 bits that is 24 pairs per report.

**The reply** is `P` `0x2A` `.` when every pair was applied on both halves. Otherwise it is
`P` `0x2A` `!`, and byte 3 names the first pair the keyboard did not apply. The host uploads
that image and every one after it the old way. A half without the icon bundle refuses the whole
report, which reads as pair 0, so a keyboard that missed the bundle still shows every icon.

**The bundle** has the font-pack layout with its own magic, `PlyI`, so the font loader can never
take an icon for a character. Each icon is stored cropped to its set pixels, with its position on
the 72 × 40 keycap. The icon ids are frozen: a new icon takes the next id, and an existing id
never changes, because the id is the only thing on the wire. The host flashes the bundle like
any other, over [BEGIN / CHUNK / COMMIT](#resource-flash-transport--begin--chunk--commit).

<Aside type="note">
Since v20 the GET_ID version block lists nine bundles and reports each one as the **lower** of
the two halves' versions. A half that missed a flash therefore reads as behind, and the host
flashes that bundle again.
</Aside>

## Mapping flags

Since **v21** (firmware 1.3.0, host 1.7.0) an app switch no longer needs its own reports to
prepare and switch on the overlays. Two bits of `SEND_OVERLAY_MAPPING_W`'s width byte do it:

| Bit | Value | Effect |
|---|---|---|
| 6 | `0x40` | **Prepare**, before the report's pairs are applied: clear the old mapping and usage bits, the same as `OVERLAY_FLAGS on` with the reset bits. |
| 5 | `0x20` | **Enable**, after the pairs are applied: show the overlays, the same as `OVERLAY_FLAGS on` with the display bit. |

The keyboard masks the width with `0x1F` before it decodes the pairs, so the value width is
unchanged (8–16 bits). A report whose masked width is out of range is refused before either flag
runs, so a malformed report changes nothing.

The host puts the prepare flag on the first mapping report of a switch and the enable flag on the
last. When the switch has to upload images first, the host still sends the prepare as its own
report, just before the first image: an image written into a slot the old mapping still shows
would otherwise appear on the old key for a moment.

**What it saves.** Counted through the host's own send path over all 60 template sets:

| Switch | Before v21 | v21 |
|---|---|---|
| Warm (every image already in the keyboard's pool) | 249 reports | 129 |
| Cold (nothing in the pool yet) | 744 reports | 684 |

A warm switch, the common case when you move between apps you use all the time, is now its
mapping reports alone.

<Aside type="note">
A keyboard older than v21 would read a flagged width byte as a width above 16 and drop the
report, so the host sets the flags only when the keyboard reports v21 or later. Older keyboards
get the separate `OVERLAY_FLAGS on` reports as before.
</Aside>

## Overlay addressing

A keycap image is addressed by **90 keycap slots × 16 modifier variants**:

```
overlay_index = keycode_slot + 90 * modifier_variant
```

Since **v12** the modifier variant is simply the modifier bitmask — bit 0 Ctrl, bit 1 Shift,
bit 2 Alt, bit 3 GUI — so all 16 combinations are addressable and the numbering is self-describing
(variant 0 = bare, 5 = Ctrl+Alt, 10 = GUI+Shift, 15 = all four). Before v12 there were 9 variants
and GUI could not be combined with anything.

That index is an **address, not storage**. It selects an entry in a lookup table that points at
one of **600 slots** in the image pool (360 bytes each, ≈ 211 KiB). Variants that share the same
artwork share a slot, so adding variants costs address space rather than image memory — which is
why v12 grew the addressable set from 810 to 1440 without needing more room for pixels.

## Protocol versions

The firmware advertises a `PROTOCOL_VERSION` (in the GET_ID string) that the host reads to decide
which commands to use. **The versions do not have to match.** The host connects to any keyboard
from v2 onwards and then gates each feature on its own:

- **Same version** — everything works.
- **Keyboard older than the host** — it still connects, and only the features that keyboard is too
  old for are greyed out, with a *"some features need a firmware update"* hint.
- **Keyboard newer than the host** — the host asks what you want to do, defaulting to a safe
  connect that sticks to the stable command set until you update the host app.
- **Older than v2** — refused, with *"Firmware too old… please update the keyboard firmware"*.
  The host cannot even list the keyboard's languages below that.

Selected milestones:

- **v2** — the **packed language list** (`0x1b`): a count byte plus one 2-byte ISO index pair per language, replacing the 4-ASCII-char legacy list. The legacy list (`0x08`) is retired and NACKs.
- **v3** — the **overlay-mapping** command (`0x15`) made **silent** (no per-chunk ACK), matching the other bulk overlay commands and removing a frequent source of stale replies.
- **v4** — **IDLE_STYLE** (`0x1c`): choose the idle anti-burn-in style (pulse / jitter).
- **v5** — a **brightness flags** byte on `SET_BRIGHTNESS` (`0x0d`): volatile vs host-auto.
- **v6** — a **per-bundle font-pack version block** appended to the GET_ID reply, so the host flashes only the bundles a keyboard is missing or behind on.
- **v9** — **GLYPH_SCRIPT** (`0x1e`): override the letter/digit legends with an alternative script.
- **v10** — the glyph script became an **open-ended index** (an unknown script renders the normal legend), so new scripts ship without a protocol bump.
- **v11** — the **plain overlay upload** (`0x0a`) packs modifier + segment into one header byte, so a full 60-byte segment fits a 64-byte report exactly.
- **v12** — **GUI combines with the other modifiers** for [app overlays](/howto/app-overlays/): `Cmd+Shift`, `Cmd+Alt` and the rest each get their own artwork instead of all falling back to the plain GUI icon, taking the addressable modifier variants from 9 to 16. The upload commands are unchanged, but the wider index space no longer fits the fixed 10-bit fields of `0x15`, so **SEND_OVERLAY_MAPPING_W** (`0x21`) was added alongside it.
- **v13** — **GLYPH_SIZE** (`0x22`): the [legend size](/using/legend-size/) — draw a key's main legend at one of three sizes, leaving the Shift/AltGr previews alone. Unlike the glyph script, the range is closed: the keyboard refuses a size it doesn't know, because an accepted-but-unrenderable size would look like a setting that does nothing.
- **v14** — **GET_LAYER_NAMES** (`0x23`): the keyboard names its own remappable layers, so the [layout editor](/using/keymap-editor/) labels its tabs from the board in front of you rather than from a list baked into the host at build time. It reports the same layer count as the existing count command, so the editor can never draw a tab it has no name for.
- **v15** — **macros** (`0x24`–`0x26`): store text or a short key sequence on the keyboard and type it back with one key, with a short **label the keycap spells out** so a row of macro keys reads `push`, `work mail`, `sign off` rather than M0, M1, M2. All three commands sit behind a single feature gate — a host that could read the macro list but not the bodies would draw an editor over data it cannot fetch. See [Macros](/using/macros/).
- **v16** — **CRASH_RECORD** (`0x27`): the firmware records a hardware fault, an unexpected exception or a watchdog restart, reboots through it, and announces it on its next boot — on the console (which the host turns into an alert) and over this command. See [when the keyboard firmware crashes](/software/reporting-problems/#when-the-keyboard-firmware-crashes).
- **v17** — a **volatile** flag on `SET_UNICODE_MODE` (`0x14`): apply a unicode mode for this session only, without storing it. It exists for the Windows logon screen, where the host cannot yet tell *WinCompose is not installed* from *WinCompose has not started yet* — so it applies its first reading volatile and only writes the mode down once it can tell the two apart. Before this, every logon on a WinCompose machine stored `Windows` and then wrote `WinCompose` back over it.
- **v18** — **IDLE_TIMEOUT** (`0x28`): how long the keyboard waits before it starts fading into the [idle style](/using/idle/#how-long-before-it-idles) becomes a setting — six presets from 15 seconds to 5 minutes — where it used to be fixed at 2 minutes when the firmware was built. 2 minutes stays the default, so a keyboard nobody touches behaves as it always did. Like the legend size and unlike the glyph script, the range is closed: a keyboard refuses a preset it doesn't know, because an accepted one would be stored and then silently resolved to some other duration.
- **v19** — **SEND_PRC_OVERLAY** (`0x29`): [PRC](#prc-predictive-range-coding) (Predictive Range Coding), a fifth keycap-image encoding that codes a typical icon to a payload of about 28 bytes. The host uses it per image, only where it saves a report; the older encodings stay.
- **v20** — **FILL_POOL_FROM_ICON** (`0x2A`): the [icon library](#icon-library-fills). Icons the app templates share are stored in the keyboard's flash, and the host sends `(pool slot, icon id)` pairs instead of their bitmaps. A cold switch into a JetBrains IDE drops from 84 reports to 32. The GET_ID version block now reports the lower of the two halves' versions per bundle.
- **v21** — [mapping flags](#mapping-flags) on **SEND_OVERLAY_MAPPING_W** (`0x21`): the prepare and enable steps of an app switch ride on the mapping reports instead of separate `OVERLAY_FLAGS` reports. A switch between apps whose images the keyboard already holds needs about half the reports.
- **v22** — **REBOOT** (`0x2B`): restart both halves without saving anything, so the host's [boot-loop test](/software/reporting-problems/#catching-a-crash-that-only-happens-now-and-then) can reboot the keyboard hundreds of times to catch a rare startup crash. Changing the handedness also reboots, but it writes the settings storage on every call.

<Aside type="note">
Not every version number above is a separate feature listed here — the list highlights the
milestones that changed the command surface. Host and firmware are still released together at the
same `PROTOCOL_VERSION`, so keeping both current is the simplest way to have everything available —
but a mismatch costs you only the newer features, not the connection.
</Aside>

Run PolyKybdHost with `--dev 2` to log the raw HID traffic — the cleanest way to see these commands and their ACK/NACK responses on the wire.
</Aside>
